## 1. Что нужно сделать (в словах постановщика)

Система усталости. Похожа на стресс в Darkest Dungeon, но **без перманентной
смерти персонажа**.

- Персонажи начинают забег с 0 усталости.
- Действия увеличивают усталость.
- Когда усталость персонажа достигает **100**, он **не может участвовать в бою**,
  пока не отдохнёт.
- Если усталость 100 **у всех** существ игрока — **забег заканчивается**.
- Усталость живёт **на `Character`** и **сохраняется после забега**. В Town
  будут отдельные способы её снимать.

### Начисление

| Событие | Когда начисляется |
|---|---|
| Бой | **в конце боя**, по исходу (пример: 10 за победу, 15 за поражение) |
| Событие | **после прохождения** узла |
| Прочие узлы (shop, rest) | по решению постановщика, начисление по типу узла |

**Доли:**

- существа **в строю** (`charactersActive`) — **полная** усталость;
- запасные (`charactersSpare`) — **половина, с округлением вверх**.

Конкретные числа за узлы на момент передачи **не утверждены** — уточнить у
владельца проекта. Твёрдо зафиксированы только: 100 = порог, active = ×1,
spare = ceil(×0.5), всё начисляется после узла.

## 3. ⚠️ Главная ловушка: `Character.serialize` — белый список

`src/character.lua:58-106` собирает сохраняемые поля **явным списком**:

```lua
local data = {
    name = c.name,
    health = c.health,
    energy = c.energy,
    prepare_x = c.prepare_x,
    prepare_y = c.prepare_y,
    attribute = c.attribute,
    element = c.element,
    level = c.level,
    exp = c.exp,
    _second_chance_available = c._second_chance_available,
    modifiers = {},
    spells = {},
}
```

Всё, чего нет в этом списке, **молча пропадает при сохранении**. Поэтому
требование «усталость сохраняется после забега» **не выполнится**, если просто
положить поле на `Character`. Нужно три места:

1. **Значение по умолчанию** — в `Character.new` (`src/character.lua:7-27`),
   рядом с `c.level = c.level or 1`. Например `c.fatigue = c.fatigue or 0`.
   Без этого старые персонажи и шаблоны из `src/characters/` дадут `nil`.
2. **Запись** — добавить `fatigue = c.fatigue` в таблицу `data` в
   `Character.serialize`.
3. **Восстановление** — в `Character.deserialize` (`src/character.lua:110-...`),
   рядом с `c.level = data.level or 1`. Использовать `data.fatigue or 0`,
   иначе старые сейвы без поля дадут `nil` и сломают арифметику.

**Обязательный тест:** сохранить персонажа с усталостью 60, загрузить,
проверить что 60. Без этого регресс незаметен.

## 4. Точки интеграции (проверено по коду)

### 4.1. Модель персонажа

| Файл | Что |
|---|---|
| `src/character.lua` | `Character.new` (дефолт), `serialize` (запись), `deserialize` (чтение) |
| `src/characters/*.lua` | шаблоны существ; `fatigue` там **не** нужен — дефолт в `Character.new` |

Персонаж — таблица; усталость — просто число `0..100`. Не заводить отдельный
модуль-синглтон: состояние принадлежит персонажу.

### 4.2. Где начисляется

**Бой** — `src/states/levelmap2.lua`, `Levelmap:resume` (~строка 484):

```lua
if from == BattleState then
    if self.currentNode.is_master_boss then
        if args.result == 'lose' then self:_handle_master_defeat(...)
        else self:_handle_master_victory(...) end
        return
    end
    ...
    if args.result == 'lose' then
        self.player.lives = self.player.lives - 1
        ...
    else
        RunState:tickBattleModifiers()
        UpgradeSelectScreen:open(...)
    end
```

Здесь есть `args.result` (`'win'` / `'lose'`) — это и есть источник «10 за
победу / 15 за поражение». Учтите **отдельную ветку босса-мастера**: она
делает `return` раньше общего кода, поэтому начисление надо поставить **до**
неё или в обе ветки — иначе за босса усталость не начислится.

**Событие** — там же, ветка `from == EventState` (~строка 532):

```lua
elseif from == EventState then
    if self.currentNode.story_scene then
        self:_handle_story_node_complete(self.currentNode)
    else
        self.currentNode.isCompleted = true
        self:_saveGame()
    end
```

Сюжетный узел идёт через `_handle_story_node_complete`, обычный — напрямую.
Начисление должно покрывать **оба** пути (или стоять в общем месте после).

**Другие состояния:** `RestState` (отдых), `ShopState` (магазин) — та же
функция `resume`, соседние `elseif`.

### 4.3. Где проверяется блокировка

`src/states/battlestate.lua:159` — `BattleState:enter` спавнит только
`charactersActive`:

```lua
for i = 1, self.player.charactersActiveSize do
    local character = self.player.charactersActive[i]
    if character then
        ...
        self:add_unit(character, true, tile)
    end
end
```

Персонажи с усталостью 100 **не должны спавниться**. Это единственная точка,
где фильтр обязателен.

### 4.4. Где заканчивается забег

`Levelmap:_handle_run_failed` (`src/states/levelmap2.lua:270`) — существующий
выход с карты:

```lua
function Levelmap:_handle_run_failed()
    self.active = false
    self.currentNode = nil
    Gamestate.pop()
    if self.cancel_target_mode then self:cancel_target_mode() end
end
```

Правило «у всех 100 → забег кончается» вызывать отсюда (или в общую точку
выхода), **не убивая жизни** — это не смерть от поражения, а истощение.

## 5. Обязательные защитные инварианты

Эти пункты — не пожелания, а условия, без которых система ломает игру.

1. **Партия никогда не должна стать пустой во время боя.** Иначе бой
   начинается без игрока, выиграть его нельзя, и это всегда поражение.
   Проверять **до** входа в `BattleState`: если после фильтра не осталось
   никого — забег завершается по правилу §4.4, а не начинается бой.

2. **Считать надо по всем, кто может выйти в бой.** Отряд — 2 слота
   (`charactersActiveSize = 2`), плюс `charactersSpare` (1). Если считать
   только `charactersActive`, spare становится бесплатной батарейкой и порог
   «у всех 100» недостижим. Решить у владельца: включать ли `charactersStables`
   — их 20, и тогда правило практически недостижимо.

3. **Порог 100 должен трактоваться одинаково везде** — в фильтре спавна, в
   проверке конца забега и в UI. Вынести в одну константу
   (например `Character.FATIGUE_MAX = 100`), не дублировать литерал.

4. **Начисление — один раз за узел.** `Levelmap:resume` может быть вызван
   повторно (возврат из UpgradeSelectScreen и т.п.). Начисление должно быть
   привязано к закрытию узла (`isCompleted`), иначе усталость начислится дважды.

5. **Не привязывать к `RunState.story`** — он обнуляется каждым
   `RunState:reset`. Усталость — на `Character`, переживает и забег, и сейв.

6. **Клампить в `[0, 100]`** при начислении и снятии. Отрицательная усталость
   или 130 сломают UI и проверки.

7. **Не смешивать с агрессивностью босса.** `master_boss_angry` управляется
   ключом `dojo_key` (`alt_when_locked`), а не усталостью. Это разные гейты.
